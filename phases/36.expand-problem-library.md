## 2. Overview

**⚠️ Read this before building anything.** The user's original request was "add the solutions of the remaining problems." A direct codebase audit (done before writing this phase) found the opposite of what that phrasing implies: **all 6 existing problems already have complete, fully authored reference solutions whose node/edge counts match their own stated stats exactly** —

| Problem | Stated stats | Actual `referenceDiagram` |
|---|---|---|
| Parking Lot | 15 classes · 13 relationships | 15 nodes · 13 edges |
| Splitwise | 10 classes · 9 relationships | 10 nodes · 9 edges |
| Elevator System | 7 classes · 4 relationships | 7 nodes · 4 edges |
| Vending Machine | 8 classes · 6 relationships | 8 nodes · 6 edges |
| Library Management | 8 classes · 7 relationships | 8 nodes · 7 edges |
| Tic-Tac-Toe | 6 classes · 5 relationships | 6 nodes · 5 edges |

There is no unfinished or stubbed solution to complete. **This phase reframes "the remaining problems" as "problems the library doesn't yet cover"** and grows the catalogue past its current 6 with new, fully authored problems and solutions — the same kind of work Phase 18 originally did, run again for new content. If this reframing is wrong and something else was actually meant (e.g., a specific problem's solution felt wrong or incomplete when observed in the running app, which this audit's static count-check wouldn't catch), redirect before building — flag whatever the actual gap was, and this phase's file/step-by-step below can be pointed at the real target instead.

**Goal (as reframed):** add **four** new canonical LLD interview problems, each with a fully authored reference solution, growing the library from 6 to 10, matching the same difficulty spread (easy/medium/hard) and pattern variety the existing 6 already have.

**Supersedes:** extends `PRD.md` §9.1's "Observed catalogue" table and Appendix A's precedent (`domain/problems/data/*.ts`) with four new entries; does not modify anything about the existing 6.

**From the user's perspective, why this is the right substitute goal:** a learner practicing repeatedly (`PHASES.md` §0.8) eventually runs out of new problems to attempt — a 6-problem library is a short runway. More canonical problems, spanning the same difficulty/pattern range, directly extends the thing this app is *for*: repeated, varied practice. This is a more useful use of effort than re-touching solutions that are already correct.

## 3. What to Build

**Files to create:** `src/domain/problems/data/lruCache.ts`, `chessGame.ts`, `movieTicketBooking.ts`, `restaurantReservation.ts` — each exporting a `Problem` object matching the exact shape used by the existing 6 (`title`, `difficulty`, `patterns`, `description`, `requirements` (4 bullets), `stats`, `referenceDiagram: { nodes, edges }`).

**Files to modify:** `src/domain/problems/index.ts` (register the 4 new entries in the `PROBLEMS` array).

**Proposed catalogue additions** (starting sketches — `// ASM:` tag each per `PHASES.md` §0.5's ambiguity-resolution protocol; refine exact member signatures while authoring, but the final `stats` string **must** match the actually-authored node/edge counts exactly, the same invariant Phase 18 enforced):

1. **LRU Cache** — `EASY` — patterns `Strategy · HashMap+DLL`. Description: "Design an in-memory cache with a fixed capacity that evicts the least-recently-used entry when full, supporting O(1) get and put." Requirements: fixed capacity set at construction; O(1) get/put; least-recently-used entry evicted on overflow; pluggable eviction policy (so a Strategy interface earns its place, not just a plain LRU). Sketch: `EvictionPolicy` (INTERFACE: `onAccess`, `onInsert`, `evict`), `LruEvictionPolicy`/`LfuEvictionPolicy` (realize it), `CacheNode` (CLASS: key, value, prev, next), `DoublyLinkedList` (CLASS), `Cache` (CLASS: capacity, orchestrates the map + list + policy) — ~5–6 classes, ~4–5 relationships.
2. **Chess Game** — `HARD` — patterns `Factory · Strategy · Template Method`. Description: "Design the core rules engine for a two-player chess game: piece movement, turn order, check/checkmate detection, and move history." Requirements: each piece type enforces its own legal-move rules; a turn-based game loop alternates players; detect check and checkmate; a move history supports replay/undo. Sketch: `Piece` (ABSTRACT: color, position; `getLegalMoves()`), `King`/`Queen`/`Rook`/`Bishop`/`Knight`/`Pawn` (CLASS, inherit `Piece`), `Board` (CLASS), `Player` (CLASS), `Move` (CLASS), `ChessGame` (CLASS, orchestrator), `MoveValidator` (INTERFACE) — ~11 classes, matching the density of the existing Parking Lot reference.
3. **Movie Ticket Booking System** — `MEDIUM` — patterns `Singleton · Observer · Strategy`. Description: "Design a system to browse showtimes, select seats, and book movie tickets with pluggable payment and booking notifications." Requirements: multiple screens/shows per movie; seat-level selection and locking during checkout; pluggable payment methods; a notification on successful booking. Sketch: `Movie`, `Show`, `Seat`, `SeatType` (ENUM), `Booking`, `PaymentStrategy` (INTERFACE) + 2 implementations, `BookingManager` (CLASS, Singleton), `BookingObserver` (INTERFACE) — ~9–10 classes.
4. **Restaurant Table Reservation** — `MEDIUM` — patterns `Aggregate Root · State`. Description: "Design a system that manages table availability and reservations across a restaurant's service hours." Requirements: tables vary by seating capacity; a reservation holds a table for a time window; table status transitions (free/reserved/occupied) as a state machine; prevent double-booking the same table/window. Sketch: `Restaurant` (CLASS, aggregate root), `Table`, `TableStatus` (ENUM), `Reservation`, `Customer`, `ReservationManager` — ~6–7 classes.

**Step-by-step per problem (same as Phase 18's original method):**
1. Author the full node list with real attributes/methods, following `PRD.md` §9.4's kind-specific seeding conventions (interfaces get at least one method; enums get literals, no members).
2. Author the full edge list with correct relationship types/labels/multiplicities per `DESIGN.md` §5.11.
3. Lay out node positions sensibly (not overlapping, roughly matching how the existing references are laid out) so `fitView()` produces a legible diagram.
4. Set `stats` to the *actual* authored counts — do not write a stat line first and author toward it; author first, then state the truth.
5. Register in `src/domain/problems/index.ts`.

## 5. Testing Framework

> No automated test files are added in this phase (or any phase in this set) — see `PHASES.md` §0.2 / §0.9. All verification below is manual: drive the running app for black-box checks, inspect `window.__store` for white-box checks.

### Black-Box Testing (User Simulation)

**Verification — Black-box:**
1. Open the Problem Library. **Expected:** 10 cards total, the grid scrolls correctly, each new card renders with the same visual treatment as the original 6.
2. Load each new problem's reference solution. **Expected:** the canvas shows exactly the number of nodes/edges the card's own stats line claims.
3. Open Issues on each new reference tab. **Expected:** "No problems" — bundled references must lint clean, the same invariant established in Phases 18–19.
4. Start Practice on each new problem. **Expected:** the Phase 31 sidebar panel correctly shows its title/difficulty/patterns/description/requirements with no special-casing needed.

### White-Box Testing (Internal State Inspection)

**Verification — White-box:**
1. `getProblems().length === 10`.
2. For each of the 4 new problems: `referenceDiagram.nodes.length` and `.edges.length` exactly equal the numbers stated in that problem's own `stats` string.

### Definition of Done (Exit Criteria)

**Definition of Done:** 10 total problems in the library, all 4 new ones lint-clean and stat-matching, zero changes required to any existing UI component to support them, and the original 6 problems are byte-for-byte unmodified.

### Scope Boundaries — Do NOT

**Do NOT:** modify any of the existing 6 problems' data files — they are already complete and correct; do NOT add more than these 4 new problems in this phase without checking in first, to keep the change reviewable; do NOT invent a 7th/8th/9th/10th problem beyond what's listed here without flagging it.
