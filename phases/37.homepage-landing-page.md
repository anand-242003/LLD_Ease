## 2. Overview

**⚠️ A note on the source material for this phase, read before building.** The user asked for a homepage "according to the picture" — no image was attached to the request, and none exists anywhere in the project or scratchpad (confirmed by direct search before writing this phase). Asked how to proceed, the user chose: no picture, build from siteinspire.com-style inspiration and a description instead — but did not supply that description in the same turn. Everything below is **this phase's own proposed content and structure**, informed by the product's own `PRD.md` (its stated executive summary, value proposition, and four core capabilities) and by general siteinspire.com-caliber landing-page conventions (bold oversized type, generous negative space, scroll-triggered reveals, alternating layouts, real product visuals over stock art). It is a complete, buildable proposal — **not** a transcription of anything the user actually specified — so treat every section below as open to redirection before or during the build.

**Goal:** a new pre-app marketing/landing route that a first-time visitor sees before the workspace, explaining what ClassForge is and why it's different, ending in a clear "launch the app" call to action — built with GSAP-driven scroll motion per the user's explicit tooling instruction.

**Supersedes:** adds to, rather than replaces, `PRD.md` §7.1 ("the application should be built as a one-route SPA... do not introduce a router library for its own sake"). This phase honors that intent by adding exactly **one** additional pre-app screen without introducing a general-purpose router — see the routing approach below. `DESIGN.md` §1's "not a marketing surface" stance is intentionally, narrowly excepted by the new §13.4 (added earlier in this iteration set) for this one route only.

**A tooling clarification, stated explicitly:** the user referred to "gsap-skills" (`npx skills add https://github.com/greensock/gsap-skills`) as the tool to use for motion. That repository is a Claude Code **skill package** (agent instructions/conventions for building GSAP-driven UI), not an npm runtime dependency — the actual code in this phase runs on the `gsap` npm package itself (core + the `ScrollTrigger` plugin). Install the skill for guidance if useful, but the app's `package.json` dependency to add is `gsap`, not "gsap-skills."

**From the user's perspective, why this matters:** right now, a link to this app drops a visitor straight into a dense, unfamiliar dark workspace — palette on the left, canvas in the middle, a four-tab panel on the right — with zero explanation of what any of it does or why it's worth their time. A first-time visitor googling "LLD interview practice" and landing cold on that workspace has no way to evaluate the product before committing to figuring it out. A homepage's job is to answer, in under a minute of scrolling: what is this, who is it for, why is it better than drawing UML in Lucidchart or just writing code in an IDE, and what do I do next — then get out of the way.

## 3. What to Build

**Files to create:** `src/components/home/HomePage.tsx`, `HeroSection.tsx`, `ProblemStatementSection.tsx`, `FeatureShowcaseSection.tsx`, `LibraryTeaserSection.tsx`, `StatsStripSection.tsx`, `HomeFooter.tsx`, `src/hooks/useHomeMotion.ts` (GSAP timeline setup + `gsap.context()` cleanup).

**Files to modify:** `src/App.tsx` (a `view: 'home' | 'app'` toggle — see Routing below), `src/components/layout/AppHeader.tsx` (brand mark becomes a click target back to the homepage), `package.json` (add `gsap`).

**Routing approach — no new router dependency:** per `PRD.md` §7.1's existing "don't introduce a router for its own sake" stance, do not add `react-router` or similar for what is fundamentally a two-state toggle. In `App.tsx`, hold a simple `view` state (`'home' | 'app'`), defaulting to `'home'` on a fresh visit. `HomePage`'s primary CTA sets `view = 'app'`. Persist a lightweight `classforge.hasVisitedApp` flag in `localStorage` once the user has entered the app at least once, so **returning users with work in progress land directly back in the app**, not the marketing page, on subsequent visits — but always leave a way back: clicking the brand mark/logo in `AppHeader` sets `view = 'home'` again. This is a pure client-side state flip, never a page reload, so in-app `localStorage` state (documents, profiles, attempts) is completely unaffected by visiting or revisiting the homepage.

**Homepage sections, in scroll order:**

1. **Hero** — full viewport height. Oversized headline (sans, sized well beyond the app's own type scale per `DESIGN.md` §13.4's permitted exception) stating the core value prop from `PRD.md` §2.3: model, get linted, get graded — not just draw. A live, GSAP-animated mock of a `ClassNode` diagram assembling itself (nodes and an edge drawing in) as the section enters view. Primary CTA button `Launch ClassForge` (teal, `DESIGN.md` §5.1 primary variant) and a secondary text link `See how it works ↓` that smooth-scrolls to section 2.
2. **Problem statement** — a short, scroll-pinned two-panel contrast: "Draw UML — no feedback" vs. "Write code — no model," resolving into "ClassForge — both," mirroring `PRD.md` §2.3's stated positioning almost verbatim (it's already good, product-truth copy).
3. **Feature showcase** — one full-bleed section per each of the four capabilities named in `PRD.md` §1's Executive Summary (visual UML editor, curated problem library, live 6-language code generator, linter + practice/scoring loop), alternating left/right image-vs-copy layout per section so no two consecutive sections repeat the same composition (a core siteinspire-style convention) — each section's "screenshot" is a real annotated mock built from the app's own mono type and component recipes, not stock art, and each reveals via a GSAP scroll-scrub as it enters view.
4. **Library teaser** — a horizontally scrolling strip previewing a handful of `ProblemCard`-styled tiles (reusing the exact `DESIGN.md` §5.7 recipe), reading the **live** problem count/catalogue rather than a hardcoded number (see Phase 36 dependency above) — clicking one launches the app directly into that problem's Practice flow.
5. **Stats strip** — an honest, factual substitute for testimonials the product doesn't have yet: e.g. "`10 curated problems · 6 languages · 4 feedback lenses`" in the app's own `mono-stat` treatment (`DESIGN.md` §3). Do **not** fabricate quotes, reviews, or user counts that don't exist — an honesty constraint, not a style preference.
6. **Final CTA + footer** — repeats `Launch ClassForge`; carries the existing `Buy me a coffee` link forward (the app's one and only monetization surface, per `PRD.md` §2.1); a minimal footer with the brand mark and, if applicable, a source-code link. No fabricated legal boilerplate (privacy policy/terms) for a product that collects no data server-side.

**GSAP specifics:**
1. `npm install gsap`; register `ScrollTrigger` once in `useHomeMotion.ts`.
2. Every timeline/ScrollTrigger is created inside a `gsap.context()` scoped to the homepage's root element and `.revert()`-ed on unmount (leaving the homepage via the CTA, or later returning to it) — no leaked triggers across the view toggle.
3. Respect `prefers-reduced-motion: reduce` per the new `DESIGN.md` §13.3: render every section's end state immediately, with scrubbing/pinning disabled entirely — not merely shortened.
4. Keep GSAP scoped to this route only — do not introduce it inside the app shell beyond one optional, subtle first-mount entrance transition the first time a visitor arrives in the app from the homepage, per §13.3's stated exception.

## 5. Testing Framework

> No automated test files are added in this phase (or any phase in this set) — see `PHASES.md` §0.2 / §0.9. All verification below is manual: drive the running app for black-box checks, inspect `window.__store`/`ScrollTrigger.getAll()` for white-box checks.

### Black-Box Testing (User Simulation)

**Verification — Black-box:**
1. Fresh browser storage → load the app's URL. **Expected:** the homepage renders, not the workspace.
2. Scroll through all six sections. **Expected:** each section's GSAP reveal triggers once as it enters the viewport, no layout jump or flash-of-unanimated-content before the timeline attaches.
3. Click `Launch ClassForge`. **Expected:** the app shell appears instantly (no page reload); if `My Design` had prior content from an earlier session, it's exactly as it was.
4. Reload the browser after having launched the app once. **Expected:** the app now loads directly into the workspace, not the homepage.
5. Click the brand mark in `AppHeader`. **Expected:** returns to the homepage; in-app data (documents, profiles, attempts) is completely unaffected by the round trip.
6. Enable OS-level `prefers-reduced-motion`, revisit the homepage. **Expected:** every section renders fully visible immediately — no scrub/pin animation plays.
7. Click a `ProblemCard` tile in the library teaser. **Expected:** launches directly into practicing that problem.

### White-Box Testing (Internal State Inspection)

**Verification — White-box:**
1. After navigating from the homepage into the app and back again (repeat a few times), run `ScrollTrigger.getAll().length` in the console. **Expected:** zero leaked instances from a previous mount of the homepage — confirms `gsap.context().revert()` actually ran.
2. Confirm `localStorage['classforge.hasVisitedApp']` is set only after the user has actually entered the app once, not on mere homepage load.
3. Confirm the library teaser's problem count is read live from `getProblems()`, not a hardcoded literal (regression-proofs it against Phase 36's catalogue growth).

### Definition of Done (Exit Criteria)

**Definition of Done:** the homepage is the default first-visit experience; all six sections are content-complete per §3 above; motion fully respects reduced-motion; the app's own `localStorage` state is never touched by visiting/revisiting the homepage; the full `DESIGN.md` §10 audit passes against this page; no leaked `ScrollTrigger` instances after repeated navigation.

### Scope Boundaries — Do NOT

**Do NOT:** add `react-router` or any general-purpose routing library; do NOT add authentication, signup, or payment UI anywhere on the homepage; do NOT fabricate testimonials, reviews, or user/download counts; do NOT let GSAP motion leak into the app shell beyond the one permitted first-mount transition; do NOT hardcode the problem count/catalogue contents in the library teaser.
