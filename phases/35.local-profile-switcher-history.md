The last of the UI-cleanup phases having landed, the app is stable enough to take on the largest data-model change in this set: giving submission history a notion of "whose history is this," without giving the app accounts, servers, or sync — none of which this product has ever had or should have (`PRD.md` §3.2/§8.1).

## 2. Overview

**Goal:** let more than one person share a single browser/machine (a study pair, a bootcamp lab computer, a sibling using the same laptop) and each see **only their own submission history and score trend**, while still sharing one canvas/workspace — because the request was specifically for a **local profile switcher for history**, not a full multi-tenant workspace system.

**Current state (confirmed by codebase research):** `src/store/persist.ts` writes one flat blob to a single `localStorage` key (`classforge.v1`) containing `documents`, `activeDocumentId`, `practiceSession`, and a single global `attempts: Attempt[]` array (`practiceSlice.ts`). There is no `userId`/`profileId` anywhere in the type system (`src/domain/types.ts`), and history is filtered only by `problemId` (`src/domain/practice/attempts.ts`). Nothing about "who" submitted an attempt exists today.

**A deliberate scope decision, stated explicitly so it can be corrected if wrong:** "profile" here means **only** a named local slot that scopes submission history (`attempts[]`) and its derived views (best score, trend chart, past-attempt review). It does **not** create a separate canvas/workspace per profile — `documents` (My Design, open reference tabs, viewport, notes, ink, stickies) stay **shared** across all profiles on this browser, because that's what "one browser, one machine, people taking turns practicing and being scored" actually implies: the *diagram on screen* is shared context (whoever is at the keyboard is looking at and editing the same canvas), but *whose history a score belongs to* is personal. If the intent was actually a fully separate workspace per profile, that is a different, larger feature — flag it and this phase can be redirected before or after building it.

**Supersedes:** deepens `PRD.md` §5.4 (client-side only) and §13 (Domain/Data Model) with a new `Profile` entity and a namespaced attempts store; the `attempts` field's storage location in the persistence contract described in `PRD.md` §16.2 changes from "inside the single workspace blob" to "one array per profile, in its own key." `PRD.md` §8.1's "there is exactly one human role" is unaffected — profiles are not roles or permissions, every profile can do everything, they only isolate history.

**From the user's perspective, why this matters:** imagine two friends prepping for interviews together, trading a laptop back and forth. Today, whoever practices second sees the first person's scores mixed into "their" history, with no way to tell which attempt was whose or to track their own improvement over time (`PHASES.md` §0.8's core promise — "practice repeatedly... see whether the learner's design is actually improving" — silently breaks the moment a second person touches the same browser). A lightweight named-profile switcher fixes this with zero setup friction: no password, no email, just "who's practicing right now" — consistent with the app's zero-signup identity (`PRD.md` §3.2/N1).

## 3. What to Build

**Files to create:** `src/store/profileSlice.ts`, `src/components/layout/ProfileSwitcher.tsx`. Add a `Profile` type to `src/domain/types.ts` (or a new `src/domain/profile/types.ts`, matching whichever convention the rest of `src/domain` already follows for small entity types).

**Files to modify:** `src/store/persist.ts`, `src/store/practiceSlice.ts`, `src/store/index.ts`, `src/components/layout/AppHeader.tsx`, and whatever component renders the submission-history/trend view built in Phase 23 (locate it first — it must keep working unchanged once attempts become profile-scoped, since it should simply keep reading the same `attempts` selector).

**Data model:**
```ts
interface Profile {
  id: string;        // nanoid, generated locally
  name: string;       // user-chosen display name, e.g. "You", "Riya"
  createdAt: number;
}
```

**Storage layout (illustrative — synthetic values, not real user data):**
- `classforge.profiles.v1` → `{ profiles: Profile[], activeProfileId: string }` — small metadata blob, always loaded on boot, never wiped by anything else.
- `classforge.attempts.v1.<profileId>` → `Attempt[]` — one key per profile, holding exactly that profile's submission history (same `Attempt` shape as today, unchanged).
- `classforge.v1` (existing key) → unchanged shape **minus** the `attempts` field, which moves to the per-profile keys above. `documents`/`activeDocumentId`/`practiceSession` stay exactly where they are — shared, not namespaced.

**Step-by-step:**
1. Add `profileSlice.ts`: `profiles: Profile[]`, `activeProfileId: string`, actions `createProfile(name)`, `renameProfile(id, name)`, `deleteProfile(id)`, `switchProfile(id)`.
2. `switchProfile(id)`: persist the outgoing profile's current in-memory `attempts` array to its own `classforge.attempts.v1.<outgoingId>` key, then load `classforge.attempts.v1.<id>` into the store's `attempts` field, then set `activeProfileId = id`. This "swap on switch" pattern means every existing consumer of `attempts` (history list, trend chart, best-score lookups) keeps working with zero changes — they don't know or care which profile they're reading, only the switch mechanism does.
3. On boot (extend `persist.ts`'s existing hydration path, which already has an established migration precedent for `localStorage` schema changes per `PRD.md` §9.0): if `classforge.profiles.v1` doesn't exist yet, this is either a fresh install or a pre-Phase-35 install.
   - **Fresh install:** create one profile named `"You"`, make it active, done.
   - **Existing install with a global `attempts` array already in `classforge.v1`:** create one profile named `"You"`, migrate the existing global `attempts` array into `classforge.attempts.v1.<newId>`, remove `attempts` from the `classforge.v1` blob, make the new profile active. Guard this migration so it runs **exactly once** (e.g. a `migratedAttemptsToProfiles: true` flag written alongside, checked before ever running it again) — never re-migrate or duplicate history on a later reload.
4. Guardrail: never allow deleting the last remaining profile — disable `Delete` on it in the UI with a tooltip explaining why; deleting any other profile permanently removes its `classforge.attempts.v1.<id>` key (make this consequence explicit in the confirm-dialog copy, not implied).
5. Build `ProfileSwitcher` per `DESIGN.md` §13.2 exactly, mounted in `AppHeader` to the left of `LLD Problems` (profile identity is the most global piece of state in the app, so it belongs at the very start of the header's reading order).
6. Locate the Phase 23 submission-history/trend view and confirm it needs **no code change** — it should already be reading the same `attempts`/`getProblemAttempts`/`getBestScore` selectors, which now transparently reflect whichever profile is active thanks to the swap-on-switch mechanism in step 2.

## 5. Testing Framework

> No automated test files are added in this phase (or any phase in this set) — see `PHASES.md` §0.2 / §0.9. All verification below is manual: drive the running app for black-box checks, inspect `window.__store` and raw `localStorage` for white-box checks.

### Black-Box Testing (User Simulation)

**Verification — Black-box:**
1. Fresh browser storage → load the app. **Expected:** profile switcher shows one profile, `"You"`, already active, with no onboarding modal forced on the user.
2. Create a profile named `"Riya"` via `+ New profile`. **Expected:** switcher now lists both; switching to `"Riya"` doesn't touch the canvas — whatever was on `My Design` a moment ago is still there, unchanged.
3. As `"You"`, practice and score Parking Lot. Switch to `"Riya"`. **Expected:** Parking Lot's history/trend for `"Riya"` is empty — `"You"`'s attempt is not visible.
4. As `"Riya"`, practice and score Parking Lot with a deliberately different design. Switch back to `"You"`. **Expected:** `"You"`'s original attempt reappears exactly, unaffected; `"Riya"`'s attempt is not mixed in.
5. Reload the page while `"Riya"` is active. **Expected:** `"Riya"` remains the active profile after reload, with her history intact.
6. Delete every profile except one, then attempt to delete the last one. **Expected:** blocked, with an explanation.
7. Delete `"Riya"` (with at least one other profile remaining) and confirm. **Expected:** her history is gone permanently; the confirm dialog's copy said this plainly before the action was taken.

### White-Box Testing (Internal State Inspection)

**Verification — White-box:**
1. Inspect raw `localStorage` directly: confirm `classforge.profiles.v1` holds `{ profiles, activeProfileId }`; confirm one `classforge.attempts.v1.<id>` key exists per profile; confirm `classforge.v1` no longer contains an `attempts` field post-migration.
2. Confirm the one-time migration flag prevents a second migration on a subsequent reload (no duplicated/doubled history after multiple reloads).
3. `window.__store.getState().documents` is provably identical regardless of which profile is active — prove this by switching profiles and confirming the document array reference/content is untouched by the switch.

### Definition of Done (Exit Criteria)

**Definition of Done:** switching profiles changes only submission-history scope, never canvas/workspace state; migration from the old single global `attempts` array is lossless and runs exactly once; at least one profile always exists and the last one cannot be deleted; the Phase 23 history/trend view works correctly per-profile with zero code changes to itself.

### Scope Boundaries — Do NOT

**Do NOT:** namespace `documents`/canvas/viewport/notes/ink per profile — that is explicitly out of scope per the deliberate decision above (flag if this was the wrong read); do NOT add passwords, emails, or any cross-device sync; do NOT auto-delete a profile's history for any reason other than the user explicitly choosing to delete that profile.
