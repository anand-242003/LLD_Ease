## 2. Overview

**Goal:** today there are **three** separate UI affordances that all lead to "see a problem's solution," and they don't agree with each other:

| Affordance | Where | Correct? |
|---|---|---|
| `Sample` header button | `AppHeader` (desktop + mobile) | **No** — hardcoded to always load the Parking Lot reference diagram into the current document, regardless of which problem is actually active. Confirmed bug, not a stylistic quirk. |
| `Load solution →` | `ProblemCard`, inside the Problem Library modal | Yes — opens the correct problem's reference tab, idempotently. |
| `Reveal reference` | `PracticeBanner` | Yes — opens the correct problem's reference tab, idempotently (same underlying action as above). |

The user's request is that a solution should be reachable from exactly **one place**. Read literally alongside the table above, the right cut is: remove `Sample` outright (it's both redundant *and* factually wrong — it doesn't even respect which problem you're working on) and remove `Reveal reference` from the banner (redundant with the Phase 31 sidebar panel's `View reference solution`, which sits right next to the rest of the problem's context). What remains is **exactly one entry point per moment in the user's journey**, which is the meaningful way to read "any one place" — not literally a single button that both a first-time browser and a mid-practice learner must hunt for in the same spot, but one clear, non-duplicated path for each:

- **Before committing to a problem** (browsing the library, deciding what to attempt) → `Load solution →` on the `ProblemCard`.
- **While already engaged with a problem** (practicing it, or viewing its reference) → the sidebar's `View reference solution` (Phase 31).

If this reframing doesn't match what was intended, it is easy to redirect before or after building this phase — flagging it explicitly here per the same convention as Phase 36's reframing below.

**Supersedes:** `PRD.md` §9.3 (Flow: Load the Sample diagram — deleted entirely; §27-U10 already rated this feature "Confidence: Low"), the `Sample` row in Appendix B and the header layout diagram in §5.1, and the `Reveal reference` row of §9.5's in-session sub-flow table.

**From the user's perspective, why this matters:** imagine practicing Splitwise and clicking `Sample` expecting to peek at *your own problem's* answer — instead you get the Parking Lot diagram, a completely different problem, dropped into your working document. That's not just redundant UI, it actively erodes trust in every other button in the header. Cutting it removes a trap. And once the sidebar already offers `View reference solution` right next to the requirements you're reading, a second identical button floating over the canvas in the banner is just visual noise duplicating a control that's already one glance away.

## 3. What to Build

**Files to modify:** `src/components/layout/AppHeader.tsx`, `src/components/canvas/PracticeBanner.tsx`.

**Step-by-step:**
1. In `AppHeader.tsx`: remove the desktop `Sample` button and its mobile-menu duplicate, the `loadSample()` handler entirely, and the `showSampleConfirm`/`ConfirmDialog` instance that gated "Replace your current diagram with the sample?". If `loadSample` had a matching store action (rather than living purely in the component), remove that too.
2. In `PracticeBanner.tsx`: remove the `Reveal reference` button and its `handleRevealReference` handler. The banner now contains only `PRACTICE` pill → title → subtitle → `Exit` (Exit itself is removed next, in Phase 34 — leave it as-is here).
3. Confirm `ProblemCard`'s `Load solution →` button and its wiring (`ProblemLibraryModal.tsx`'s `handleLoadSolution`) are **untouched** — this remains the correct browsing-time entry point and needs no changes.
4. Confirm the Phase 31 sidebar panel's `View reference solution` action is the **only** remaining working-time entry point, and that it calls the exact same `loadReferenceDiagram(problemId)` action as `ProblemCard` — there should be exactly one implementation of "open this problem's reference tab" in the whole codebase, called from exactly two places (library card, sidebar panel) that serve two different moments.
5. Re-flow the header (again) now that `Sample` is gone, alongside Phase 30's Export/Import removal — the header should now read, in order: `LLD Problems` … `Clear` … (`Score my solution` in Practice) … `Buy me a coffee`.

## 5. Testing Framework

> No automated test files are added in this phase (or any phase in this set) — see `PHASES.md` §0.2 / §0.9. All verification below is manual: drive the running app for black-box checks, inspect `window.__store` for white-box checks.

### Black-Box Testing (User Simulation)

**Verification — Black-box:**
1. Load the app. **Expected:** no `Sample` button anywhere (desktop header, mobile menu).
2. Start Practice on Splitwise. **Expected:** the banner shows no `Reveal reference` button; the sidebar panel's `View reference solution` opens the **Splitwise** reference tab, not Parking Lot — proving the old hardcoded bug is gone.
3. Open the Problem Library, click `Load solution →` on Vending Machine. **Expected:** unchanged regression — the correct Vending Machine reference tab opens.
4. From the sidebar panel while practicing Vending Machine, click `View reference solution` a second time after the tab is already open. **Expected:** the existing tab is refocused, no duplicate tab is created (same idempotency guarantee as Phase 19).

### White-Box Testing (Internal State Inspection)

**Verification — White-box:**
1. Repo-wide search for `loadSample`/`Sample` (as a feature identifier, not the English word elsewhere) returns zero remaining references in `src/`.
2. Confirm there is exactly one function in the codebase implementing "load/focus a problem's reference tab" (`loadReferenceDiagram`), called from exactly two call sites.

### Definition of Done (Exit Criteria)

**Definition of Done:** `Sample` is fully removed (button, handler, confirm dialog, any store action); `Reveal reference` is removed from the banner; the sidebar panel and the library card are the only two remaining ways to view a solution, each correctly scoped to its own moment in the user's journey; the Parking-Lot-only bug cannot recur because the buggy code path no longer exists.

### Scope Boundaries — Do NOT

**Do NOT:** touch `Load solution →`/`ProblemCard`/`ProblemLibraryModal` — they are already correct and are the intended browsing-time entry point; do not touch `Exit` yet (Phase 34); do not remove `loadReferenceDiagram` itself — it is still actively used by two call sites.
