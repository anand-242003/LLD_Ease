## 1. Relationship to Previous Phase

**Depends on:** [Phase 30 — Remove Import / Export](./30.remove-import-export.md)

Builds the first genuinely new surface in this phase set: a persistent problem-context panel in the left `PaletteSidebar`. This phase is deliberately additive-only — it must land and be verified before Phases 32 and 33 remove the two UI affordances (`Brief` dialog, `Reveal reference`/`Sample` sprawl) whose job it is about to absorb.

**What the next phase assumes:** Phase 32 assumes this panel already renders the full problem brief (title, description, requirements) correctly in both Practice and Reference-tab contexts, per this phase's Definition of Done — it deletes the `Brief` modal because this panel already shows the same content persistently.

---

## 2. Overview

**Goal:** whenever a problem is "in scope" — the user is either practicing it or viewing its reference solution — show that problem's context (title, difficulty, patterns, description, requirements) **persistently in the left sidebar**, not buried in a modal or a truncated one-line banner subtitle.

**Supersedes:** deepens `PRD.md` §10.3 (`PaletteSidebar`) with a new top region; the recipe is `DESIGN.md` §13.1 (added in this iteration set). Reduces the load-bearing responsibility of `PRD.md` §10.4.1's `PracticeBanner` subtitle line, which stays as a lightweight identity reminder rather than the only place the problem's name shows up while modeling.

**From the user's perspective, why this matters:** today, once you start practicing a problem, the *only* on-screen reminder of what you're actually solving is a truncated one-line subtitle floating over the canvas (`"Model the classes & relationships, th…"`) — the full requirements only exist behind a `Brief` button that opens a modal **over the canvas you're actively working on**. That means every time you want to double-check "wait, did the brief say floors have *typed* spots, or just spots?", you have to stop modeling, open a modal, read it, close it, and reorient. The palette sidebar is already the one part of the screen that's always visible and never covers your work — it's where the "verbs" (add a class, draw a relationship) already live. Putting the "what am I even building" context there too means a learner can glance left and see both *what to do* and *what to build* at once, without ever losing sight of the canvas.

## 3. What to Build

**Files to create:** `src/components/layout/ProblemContextPanel.tsx`.

**Files to modify:** `src/components/layout/PaletteSidebar.tsx`, `src/store/selectors.ts`, `src/store/uiSlice.ts` (ephemeral expand/collapse UI state only — not persisted to `localStorage`, since re-reading a brief you already expanded once per session is a fair default to reset).

**Step-by-step:**
1. Add a selector, e.g. `selectActiveProblemContext(state)`, that resolves to a `Problem | null`:
   - if the active document is read-only and has a `sourceProblemId` → `getProblem(sourceProblemId)`;
   - else if `practiceSession != null` → `getProblem(practiceSession.problemId)`;
   - else → `null`.
2. Build `ProblemContextPanel` per `DESIGN.md` §13.1 exactly: difficulty badge (§5.6) + title (2-line clamp) + pattern tags (teal, middle-dot joined, reusing the `ProblemCard` treatment) + description (3-line clamp with an inline "Show more" text toggle, no modal) + requirements list (revealed only when expanded) + a footer action button labeled `View reference solution`.
3. Wire the footer action to the **existing** `loadReferenceDiagram(problemId)` store action (already built in Phase 19 — do not reimplement it). This is a real, working action from day one of this phase, not an inert stub — unlike Phase 18's original convention, there is no reason to stub something that already exists and already does the right thing.
4. Hide the footer action (not just disable it) when the active document *already is* that problem's reference tab — clicking it there would be a no-op refocus of the tab you're already looking at, which is confusing rather than harmful. Show it whenever practicing (so a learner can jump to the reference without detouring through the header or the library).
5. Mount `ProblemContextPanel` at the very top of `PaletteSidebar`, above the `ADD CLASS · DRAG ONTO CANVAS` section. When `selectActiveProblemContext` returns `null` (ordinary free-form modeling on `My Design` with no practice session), render **nothing** — zero height, no placeholder empty state, no reserved gap. The common case (just modeling, no problem in scope) must look exactly as it did before this phase.
6. Responsive: on tablet/mobile widths where Phase 28 turned the palette into a drawer/bottom-sheet, the panel appears at the top of that drawer's/sheet's content, using the same recipe.
7. Accessibility: the "Show more" toggle is a real `<button>` (keyboard-reachable, `aria-expanded`), not a `<span>` with a click handler; the requirements list, when expanded, is a real `<ul>`.

## 4. UI & Design Requirements

**Relevant DESIGN.md sections for this phase:** §13.1 (new recipe this phase implements), §5.6 (Badge), §5.7 (Card, for the pattern-tag treatment reused here), §7 (Motion — the expand/collapse animates per the standard `--dur-base` rule and collapses to 1ms under reduced motion).

**UI consistency checklist:** panel uses `--surface-2`/`--border`/`--r-md` exactly per §13.1, not a bespoke surface color; description/requirements text is `body-sm`/`text-muted` (chrome, sans) while the problem title still counts as chrome too (it's the app describing the problem, not model content the user authored) — do **not** render it in `mono-node`; teal appears only on the pattern tags (which mirror the existing `ProblemCard` convention) and the "Show more"/footer action, never as decoration.

## 5. Testing Framework

> No automated test files are added in this phase (or any phase in this set) — see `PHASES.md` §0.2 / §0.9. All verification below is manual: drive the running app for black-box checks, inspect `window.__store` for white-box checks.

### Black-Box Testing (User Simulation)

**Verification — Black-box:**
1. With `My Design` active and no practice session running, look at the sidebar. **Expected:** no problem panel, no gap, sidebar looks exactly as it did before this phase.
2. Start Practice on Elevator System. **Expected:** the panel appears above `ADD CLASS`, showing the `HARD` badge, title `Elevator System`, patterns `Strategy · State`, a clamped description, and a `View reference solution` footer button.
3. Click "Show more". **Expected:** description expands in place to full text, the 4 requirement bullets appear below it, no modal opens.
4. Click `View reference solution`. **Expected:** the Elevator System reference tab opens/focuses (same behavior as `Load solution →` in the library), and the panel's footer action is now hidden since that reference tab is the active document.
5. Switch back to the `My Design` tab mid-practice. **Expected:** the panel reappears (the practice session is still active) and its footer action is visible again.
6. End up with no problem in scope (no practice session, on `My Design`, no reference tab active). **Expected:** panel disappears completely again.

### White-Box Testing (Internal State Inspection)

**Verification — White-box:**
1. `window.__store.getState()` — call the new selector directly in each of the three states above (no problem / practicing / viewing a reference tab) and confirm it returns `null`/the correct `Problem` object each time.
2. Confirm the selector is a pure derivation with no independent state to desync — switching documents or starting/leaving practice never requires a manual "refresh."

### Definition of Done (Exit Criteria)

**Definition of Done:** the panel shows correct, complete problem context in both qualifying states, is fully absent otherwise, matches `DESIGN.md` §13.1, and its footer action correctly reuses the existing `loadReferenceDiagram` action with no duplicated logic.

### Scope Boundaries — Do NOT

**Do NOT:** remove the `Brief` button/dialog or the `Reveal reference` button yet (Phases 32 and 33) — this phase only adds the new panel; do not touch `Sample`; do not persist the expand/collapse state to `localStorage`.
